## 一、结论速览

| 版本 | 单帧墙钟 | **端到端 fps** | 推理管线 fps | 相对基线 |
|---|---|---|---|---|
| 基线（生产配置 `save_mode=images`） | 152.05 ms | 6.577 | 7.40 | — |
| **Round 1**：绘图 + 落盘移出主循环 | 139.65 ms | **7.161** | 7.40 | **+8.9%** |
| **Round 2**：CUDA 流解耦 | 138.53 ms | **7.219** | 7.47 | +0.8% |
| **合计** | **−13.5 ms** | **+9.8%** | ≈0 | 精度无变化 |

**一句话结论**：本轮把主循环里 17.2ms 的纯 CPU 串行时间（绘图 7.16ms + JPEG 落盘 10.05ms，期间 GPU 完全空转）
挪到独立工作线程，与下一帧的 GPU 推理重叠，端到端吞吐 **6.577 → 7.219 fps（+9.8%）**；
模型、输入分辨率、帧率策略均未改动，检测框/深度输出逐比特一致。

**同时确认了一件事**：优化后流水线 **96.4% 的时间是 GPU 推理本身**，CPU 侧已基本榨干。
后续要再上一个台阶，只能动 GPU 侧的模型/精度/帧率策略（见第七节）。

**摄像头实测（最终构建）**：板上 USB 摄像头 640×360 输入，推理管线 **7.60 fps**、
端到端 **7.1–7.5 fps**，输出 640×720 拼接图（RGB + 深度半区完整），全链路无崩溃。

### 2.2 双口径 fps（关键）

主循环同时打印两个数，避免自欺：


> 只看「推理管线 fps」会得出「优化没效果」的错觉：本轮优化把工作从**墙钟路径**搬到了推理之外，
> 所以 pipeline fps 几乎不变（7.40 → 7.47），而 wall fps 涨了 9.8%。**这才是真实吞吐。**

## 四、Round 1：把绘图 / 落盘移出主循环（+8.9%）

### 4.1 改动

新增 `DrawSaveWorker`：一个有界队列（容量 2）+ 独立线程的「延后绘制 + 落盘」执行器。
主线程只负责把**纯数据**拷出来交给它。

```
改前（单帧 152ms，GPU 有 17ms 是闲的）
  读帧 → 推理 135ms → 绘图 7.2ms → concat → JPEG 10.0ms → 下一帧
                       └──────── GPU 空转 ────────┘

改后（单帧 139ms，CPU 侧只剩零星小拷贝）
  读帧 → 推理 135ms → concat 4.7ms → collect 0.005ms → enqueue 0.06ms → 下一帧
                            │
                            └──→ [工作线程] 绘图 7.2ms → 唤醒显示 → JPEG 10.0ms
                                        （与下一帧 GPU 推理重叠）
```

**关键设计点**

- **任务必须自带全部数据**：`out_frame` 由 `concatenateFrames()` 独立分配（1280×1440 BGR ≈ 5.5MB）。
  - `raw_img` 属于帧槽位（读帧线程立刻复用）；
  - `depth_vis` **直接包在深度模型的 pinned 主机缓冲上**（下一帧深度的 D2H 会覆盖它）。
  - 不拼进独立 buffer 就会数据竞争 —— 这也是为什么 `04.concat` **不能**一起搬到工作线程。
- **颜色在主线程解析**：`pipeline.getColor()` 依赖 tracker 状态，避免与下一帧更新竞争。
- **绘制写在上半区视图**：`task.out_frame(cv::Rect(0,0,img_w,img_h))`，零像素拷贝，
  且 `drawTrackedObject` 内部的边界裁剪仍是原图尺寸（保持视觉一致）。
- **显示要看到「已绘制」的帧**：`drawn_signal`（`promise<void>`）在工作线程画完后立刻 `set_value()`，
  主线程 `wait()` 后再 `imshow`；**JPEG 编码/写盘继续在后台跑**，不让主线程等。
- **析构顺序**：`DrawSaveWorker` 声明在 `io_manager` / `drawing_manager` **之后** →
  反向析构时先把队列排空并 `join`，之后才轮到两个管理器析构。

## 五、Round 2：CUDA 流解耦（+0.8%，**负结论为主**）

### 5.1 假设

`p1.depth_launch` 稳态 **12.8ms**、`p2.yolo_launch` **8.2ms** —— 对「发射」阶段来说长得离谱。
排查发现两处 legacy default stream 耦合：

1. `io_manager.cpp` 的帧 H2D：`cudaMemcpyAsync(...)` **不传 stream** → 走 **legacy default stream**；
2. `base_model.cpp`：`cudaStreamCreate(&stream_)` → 创建的是 **blocking stream**。

按 CUDA 语义，legacy default stream 上的操作会与**所有 blocking stream** 互相插入隐式依赖。
于是读帧线程每帧的 H2D 会和主线程的 TRT `enqueueV2` 互相串行化。

（同一类问题上一轮已经踩过一半：`frame.h` 里留有注释「pageable 内存直接 `cudaMemcpyAsync`
会触发驱动内隐式设备同步，与主循环 TRT enqueueV2 撞车（实测 Depth 发射 49ms vs 12ms）」。）

### 5.2 改动

```cpp
// 1) 帧 H2D 改走专用「非阻塞」拷贝流，并在推入队列前同步本流
CHECK_CUDA(cudaStreamCreateWithFlags(&h2d_stream_, cudaStreamNonBlocking));
CHECK_CUDA(cudaMemcpyAsync(d_raw_img_, h_pinned_, img_size,
                           cudaMemcpyHostToDevice, h2d_stream_));
CHECK_CUDA(cudaStreamSynchronize(h2d_stream_));   // 只等本流，不与推理流互相阻塞

// 2) 两个模型的推理流同样改为非阻塞
CHECK_CUDA(cudaStreamCreateWithFlags(&stream_, cudaStreamNonBlocking));
```

读帧线程每帧有 ~130ms 余量，等这 2.7MB 拷完（~1ms）零代价；
换来的是模型侧**无需任何跨流 event 等待**即可直接读到 GPU 上的当前帧，
同时保证了 pinned 源缓冲复用前上一帧的 DMA 已收尾。

### 5.3 实测（`~/prof/o3.log` / `o4.log`）—— 结果是**否定的**

| 探针 | Round 1（o1） | Round 2（o3） | 变化 |
|---|---|---|---|
| **00.wall/frame** | 139.649 ms | **138.526 ms** | **−1.12 ms（−0.8%）** |
| 02.infer_pipeline | 135.254 | 133.983 | −1.27 |
| **p1.depth_launch** | 17.448（稳态 12.81） | **17.637（稳态 12.83）** | **≈0** |
| **p2.yolo_launch** | 8.218 | 7.930 | −0.29 |
| p3.yolo_wait | 113.698 | 112.464 | −1.23 |
| 04.concat | 4.735 | 4.747 | ≈0 |
| **端到端 fps** | 7.161 | **7.219** | **+0.8%** |

**`depth_launch` 12.8ms 纹丝不动** → **原假设被数据推翻**。

**那这 12.8ms 到底是什么？** 排除法后剩下的解释是
**TensorRT `enqueueV2` 本身的 CPU 侧发射开销**：
Depth（Lite-Mono-Tiny）层数远多于 YOLOv8n（8.2ms），在 4 核 Cortex-A57 上
逐层 launch 数百个 kernel，12.8ms 与层数量级吻合。
这属于**硬件 + TRT 版本的固有成本**，改 stream 标志位无法消除。

> **诚实记录**：Round 2 只带来 0.8%，**不构成性能优化**。
> 保留它的理由是它消除了一个真实的隐式同步隐患（正确性/鲁棒性改善），
> 而不是因为它快。**真正的性能收益全部来自 Round 1。**
> 如果不信这个结论，见第七节的验证建议：用 CUDA Graphs 把那 12.8ms 一次性打掉。

## 七、剩余空间与建议（按性价比排序）

优化后 `infer_pipeline` 占墙钟 **96.4%**，其中：

- **CPU 侧发射**（TRT enqueue）：`depth_launch` 12.8 + `yolo_launch` 7.9 ≈ **20.7ms**
- **GPU 侧执行**：其余 ≈ **128ms**（`p3.yolo_wait` 112.5ms 就是在等 GPU 把两模型的 kernel 跑完）

> 📌 本段原先写的是「≈112–115ms，深度约占 85ms、YOLO 约占 30–50ms」—— 那是用 `depth_interval: 2`
> **反推**出来的估计。后续用 `trtexec --loadEngine` 的 `GPU Compute Time` **直接实测**得到：
> **YOLOv8n 50.11ms + Lite-Mono-Tiny 77.76ms = 127.9ms**，占单帧墙钟的 **92.4%**。
> 反推把深度高估了 7ms、把 YOLO 低估了 0–20ms —— **能直接测就别反推**。

### 7.0 先给结论：纯 CPU 侧优化已经到顶（上界 +3.4%）

这是本报告最该被记住的一段，**它推翻了本文档早期版本给出的乐观估计**。

**上界证明（只用已有数据，不需要新测量）**

1. `p3.yolo_wait` 同步了 yolo 流、`p5.depth_wait` 同步了 depth 流，两者都在 `processOverlap()`
   **返回之前** → **本帧的全部 GPU 工作必须在这 134ms 内跑完**，即 `GPU忙时(每帧) ≤ 134ms`。
2. 帧时间 ≥ 每帧 GPU 忙时（GPU 必须把这活干完）。
3. 当前帧时间 138.5ms，其中 `04.concat` 的 4.75ms 期间 GPU 确实空转（两条流都已同步完）。

→ **任何纯 CPU 侧重构的绝对上限 = 134ms → 7.46 fps，相对当前 7.219 最多 +3.4%。**

更关键的是：`t≈0.2ms` 深度预处理 kernel 一发射、GPU 就开工了，之后 12.6ms 的 `enqueueV2`
和 7.9ms 的 yolo 发射**都是在 GPU 忙着的时候**做的 —— **那 20.7ms 早就被隐藏了**。
所以「把 20.7ms 发射藏进 112ms 等待」这个说法本身是错的：没有 20.7ms 可以藏。

（修正前本文档写的是「天花板 7.5–8.5 fps，+4%~+17%」，那是默认发射发生在 GPU 开工之前算出来的，
与实测时间线矛盾。）

### 建议 1（唯一有意义的杠杆）：`depth_interval: 2`

```yaml
depth:
  depth_interval: 2      # 深度每 2 帧更新一次，中间帧复用缓存（浅拷贝，零像素拷贝）
```

配置项已存在、代码已支持（`Pipeline` 内部 `depth_frame_counter_` + `cached_depth_vis_`）。

✅ **已实测确认**（2026-09-16，当前构建 `bin_opt2`，d1/d2 在**同一会话**连跑）：

| 配置 | 单帧墙钟 | 端到端 fps | 推理管线 fps |
|---|---|---|---|
| `depth_interval: 1`（对照） | 138.50 ms | 7.220 | 7.47 |
| `depth_interval: 2` | **99.91 ms** | **10.009（+38.6%）** | 10.50 |

粗估的 9.9 fps 与实测 10.01 fps 只差 1% —— 「反推 + 上界法」这套估算在本项目上够准。
`p1.depth_launch` 的 n=150（总 300 帧）证实隔帧确实生效。

⚠️ **但平均值会骗人**：帧时间是**双峰**的 —— 跑深度的帧 ≈134ms（7.5 fps）、跳过的帧 ≈56.6ms（17.7 fps）
（由 `2×99.91 − 133.98` 反推快簇；`infer_pipeline` 的 P95=134.27ms ≈ d1 的 133.98ms 就是证据）。
**帧间隔在 57↔134ms 之间跳变**，下游若假定恒定帧间隔（播放器缓冲、编码器码率、告警节流）
必须按最坏帧时间设计。给业务方只报 avg 是耍流氓。

代价（三处，后两处最容易漏）：

1. 深度信息最旧滞后 1 帧（≈135ms）。
2. `updateMotionStates()` **每帧都执行**，非深度帧直接用 `cached_depth_` → 卡尔曼滤波拿到的是
   **当前帧 `timestamp` + 上一帧 depth 测量值**的错配组合 → 速度/加速度估计有**系统性偏差**，
   不是单纯「显示慢一帧」。业务若对「趋近 / 远离」判定敏感需单独评估。
3. `depth_vis` 走的也是 `cached_depth_vis_` → **存出的 jpg 深度半区与 RGB 半区差一帧**。

**属于业务/精度取舍，需产品确认后再启用**，不适合由优化方单方面改。

### 建议 2（已降级为「不建议做」）：软件流水

把 `processOverlap()` 拆成 `launch(N)` + `collect(N-1)`，并给两个模型各配双缓冲 I/O
（当前 `d_infer_io_` 每模型只有一套，帧 N+1 的推理会踩掉帧 N 的结果）。

- **收益上界：+3.4%**（见 7.0 节的上界证明）—— 因为被隐藏的 20.7ms 其实早就在 GPU 忙时里了
- **代价**：跨帧状态（tracker / 深度缓存 / motion records）全部要按帧号重排、I/O 双缓冲
  额外 15–20MB、2 槽位帧池可能要到 3 槽
- **结论**：改动面大而收益 ≤3.4%，**不划算，不建议投入**

### 建议 3（同受上界约束）：CUDA Graphs

静态形状已满足（`1×3×640×640` / `1×3×192×640`），把整条 enqueue 链捕获成一张图回放，
理论上能把 20.7ms 压到亚毫秒级。**但按 7.0 节，收益同样 ≤ +3.4%**，
且**已用 `trtexec --useCudaGraph` 实测否决**：19.771 vs 19.735 qps = **+0.2%**。

原因也已查清：`1/Throughput` 与 `GPU Compute Time` 只差 0.5–0.9ms，说明**帧内根本没有气泡** ——
没有气泡就没有「等 GPU」的时间可供 CUDA Graphs 去节省。**此项关闭，不要再投入。**

（原风险提示保留备查：TRT 8.2 捕获期间若有内部 `cudaMalloc` 会失败；每帧槽位指针不同，
需要每槽一张图或先拷进固定输入缓冲。）

### 建议 4（工程卫生，不影响稳态 fps）

- `main` 的 RUNPATH 从绝对路径改为 `$ORIGIN` —— 否则任何 A/B 都活在「加载错库」的阴影里
- `loadEngineFromShm()` 接到 `loadEngine()` 里（省每次启动 10–20s 引擎反序列化）
- `IO_manager.h`：`has_cuda_` 名字容易误导（是「CUDA 可用性缓存」，不是「使用了 CUDA」）

## 十一、更正与补充（同日深夜：引擎构建质量 + kernel 级真实成本）

**这一节的起因**：第七节写完「纯 CPU 侧到顶、出路只剩 `depth_interval` 和换模型」之后，
被追问「社区/官方还有没有别的方法」。为了把这个问题变成算术题，改用 `trtexec` / `nvprof`
在**模型外部**直接量 GPU 时间 —— 结果推翻了本文档前面两处结论。

### 11.1 ⭐ 最大的意外：现役引擎是「建坏了」的

**做法**：拿**同一个 ONNX** 用最朴素的参数裸重建一遍，与现役引擎对照。
这件事应该在**任何**「优化到头了」的结论之前做，我们做晚了。

| 引擎 | GPU Compute Time |
|---|---|
| 现役 `..._fp16_trt8.2.engine` | **94.32 ms** |
| 现役 `..._int8_trt8.2.engine` | **77.70 ms** |
| 裸重建 `--fp16 --workspace=2048` | **78.09 ms** |

**裸 fp16 重建比现役 fp16 引擎快 16.2ms（−17%），直接追平现役 INT8。**
最可能的原因是 **`--workspace` 太小**：`trtexec` 默认只有 **16MB**，TRT 拿不到大
tile / winograd 算法所需的 scratch 显存，只能退到 FP32 sgemm —— 与 `nvprof` 看到的
「29 次/帧 FP32 sgemm」完全吻合。

> 📌 **通用纪律：拿到一个「已优化」的引擎，第一件事是自己从 ONNX 重建一遍做对照。**
> 构建参数（workspace / timing cache / tacticSources / 构建机）任何一个不同都可能差 10–20%。
> 「引擎是别人给的」本身就是一个未经验证的假设。

### 11.1b 第二次对照：结论反转 —— 重建 INT8 并没有增益

顺着 11.1 的思路，用 `--workspace=2048` + 200 帧熵校准重建了**现役那个 INT8 引擎**，
同一次会话内三方对照：

| 引擎（同一会话内测量） | Throughput | GPU Compute Time |
|---|---|---|
| 现役 INT8（仓库预置） | 12.6756 qps | **77.75 ms** |
| **重建 INT8**（`--workspace=2048` + 200 帧校准） | 12.6522 qps | **78.05 ms** |
| 裸重建 FP16（`--workspace=2048`） | 12.6582 qps | **78.06 ms** |

**三个引擎落在 0.4% 之内，所以：**

1. **重建 INT8 零增益**（78.05 vs 77.75，差异在噪声内）→ **现役生产引擎本来就是建好的**，
   不存在「重建一下白得 11%」。11.1 里被建坏的只有**不用于生产**的 fp16 引擎。
2. **在 sm_53 上，构建良好的 FP16 ≈ INT8**（78.06 vs 77.75，差 0.4%）
   → 11.3 那张「INT8 比 FP16 快 17.5%」的表，是**拿建坏的 FP16 当对照组**得出的，
   **该数字不能用来支持「INT8 更快」**。INT8 的价值在**显存占用**（4GB 板上不无小补），不在延迟。
3. 深度模型在这张卡上的**延迟底线就是 ~78ms** —— 与精度选择、与是否重建都无关。
   这从另一侧加固了「出路只剩 `depth_interval` / 换更轻的模型」。

> 📌 **比结论更重要的纪律：对照实验的「对照组」本身必须先被验证。**
> 两次对照各自都对，但第一次推导出的「INT8 快 17.5%」错在把**一个被建坏的 fp16 引擎**
> 当成了 FP16 的正常水平。**任何 A/B 结论都要多问一句：对照组是健康的吗？**
> 本次证伪它只用了一条命令（同会话 `trtexec --loadEngine` 三方对比），成本极低。

全过程耗时（要留足时间）：**校准 200 批 ≈ 6min + 构建 ≈ 17min = 1374s（≈23 分钟）**。

**构建期其它旋钮（扫描结果全是负结论，别重复试）**：

| 变体 | GPU Compute Time | 结论 |
|---|---|---|
| `--fp16 --workspace=2048`（对照） | 78.09 ms | ✅ |
| `--tacticSources=-CUDNN` | 103.65 ms | ❌ 更差 33% |
| `--tacticSources=-CUDNN,-CUBLAS,+CUBLAS_LT` | 105.21 ms | ❌ 更差 |
| `--directIO` | 78.09 ms | ➖ 打平，无增益 |
| `--int8`（不给校准数据） | ≈ fp16 | ❌ 无意义，缺 dynamic range 的层整体退回 FP16 |

**构建耗时（要有耐心）**：Lite-Mono-Tiny 单次构建 **约 9–10 分钟**；
INT8 还要先跑 200 批熵校准（**1.76s/批 ≈ 6 分钟**）。多变体扫描务必写脚本丢后台。

### 11.2 逐层剖析的 1.5× 陷阱（差点误判）

`trtexec --dumpProfile` 的逐层耗时表**绝对值不可信**：表求和 **75.55ms** 而
`GPU Compute Time` 只有 **50.11ms**（YOLO），差 1.5×。
两个真实伪影（差一点就去重构检测头了）：

| 条目 | 表里显示 | 真相 |
|---|---|---|
| `{ForeignNode[/a/.../b]}` × 3（深度模型） | 15.4 + 9.4 + 5.3 = **30.1ms** | 归因伪影。`表总和 − GPU Compute = 27.1ms` ≈ 正好这 3 个 |
| `/model.22/dfl/conv/Conv`（YOLO） | 25.9ms =「YOLO 一半算力」 | 归因伪影。`表总和 − GPU Compute = 25.4ms` ≈ 正好它 |

**识别技巧**：伪影条目的值**在不同精度下几乎完全相同**（15.424 / 15.443 / 15.404ms）——
真 kernel 的耗时会随精度变化，一个不随精度变的「耗时」必然是仪器归因伪影。
**解读逐层表前必须先做 `1/Throughput ≈ GPU Compute Time` 交叉验证。**

### 11.3 精度三档实测：别信「Nano 上 INT8 没用」

官方论坛常答「INT8 需要 Tensor Core（sm>7.x），Nano 请用 FP16/FP32」。
**结论对、理由不成立**：Maxwell（sm_53）确实没有 Tensor Core 也没有 DP4A，
但 TRT 8.2 仍会发射 INT8 kernel，省的是**内存带宽**（权重/激活 4× 变小）。

| engine | INT8 | FP16 | FP32 |
|---|---|---|---|
| Lite-Mono-Tiny @192×640 | **77.76 ms** | 94.30 | 98.19 |
| YOLOv8n @640×640 | **50.11 ms** | 52.16 | — |

> ⚠️ **本表已被 11.1b 部分推翻**：FP16 那一列的 94.30ms 是**建坏的**现役 fp16 引擎。
> 重建后 fp16 = **78.06ms**，与 INT8 的 78.05ms 打平。
> 所以「INT8 比 FP16 快 17.5%」**不成立**；正确的表述是
> **「在构建良好的前提下，INT8 与 FP16 延迟相同，INT8 的优势只在显存」**。
> YOLO 那一列的 int8/fp16 差异（50.11 vs 52.16，3.9%）未做重建复核，同样建议存疑。

→ **正确的做法不是「按说法选」，也不是「按这张表选」，而是：先把两者的构建参数对齐，再做同会话对照。**

### 11.4 kernel 级真实成本（`nvprof`，基线构建，单帧）

| 类别 | ms/帧 | 占比 | 次/帧 |
|---|---|---|---|
| **FP32 GEMM (sgemm)** | 23.81 | 17.1% | 29 |
| winograd / cuDNN 卷积 | 22.41 | 16.1% | 32 |
| TRT pointwise（生成内核） | 20.26 | 14.5% | **98** |
| 其它 | 18.30 | 13.1% | 63 |
| `__myl_*`（融合激活 / Norm / gating） | 12.03 | 8.6% | 34 |
| INT8 layout 转换 | 6.79 | 4.9% | 42 |
| Reformat / Copy | 6.59 | 4.7% | 21 |
| grouped / direct 卷积 | 6.44 | 4.6% | 17 |
| Slice / Concat / Shuffle | 4.81 | 3.5% | 7 |
| Resize | 3.97 | 2.8% | 7 |
| 自研 CUDA kernel | 3.52 | 2.5% | 3 |
| FP16 GEMM (hgemm) | 3.29 | 2.4% | 10 |
| Softmax | 2.11 | 1.5% | 1 |

三个结论：

1. **卷积只占约 35%** —— 别默认「卷积是瓶颈」。
2. **非数学的图层开销**（pointwise + INT8 layout + reformat + slice + transpose + memcpy）
   ≈ **43.6 ms/帧 = 31%**，由 ONNX 图形态造成，不是模型算力需要的。
3. **29 次/帧的 FP32 GEMM = 23.8ms 全部来自深度模型**（单测深度引擎可复现 29 次 / 23.5ms），
   来自 Lite-Mono 的注意力 MatMul。FP16 hgemm 只有 3.0ms → **GEMM 占深度模型 34%，
   其中 88% 跑在 FP32 上**。`__myl_*` 的 kernel 名直接写着融合内容
   （`...AddDivErfAddMulMul` = Erf 版 GELU，`...MeaSubMulMeaAddSqrDiv...` = LayerNorm），
   是免费的模型结构情报。

> ⚠️ `nvprof` 的绝对值也带仪器开销（本次合计 139.45ms vs 真实 GPU 忙时 127.9ms，约 9% 膨胀），
> **相对占比可用，绝对值请以 `trtexec` 的 `GPU Compute Time` 为准**。

### 11.5 帧时间账目闭合 + CUDA Graphs 实测否决

- GPU 实测合计 **127.9ms**（YOLO 50.1 + Depth 77.8），占单帧墙钟 **92.4%**
- **账目完全闭合**：`138.5 = 50.1(YOLO) + 77.8(Depth) + 6.1(app 侧 CPU) + 4.75(concat)`
- `1/Throughput` 与 `GPU Compute Time` 只差 0.5–0.9ms → **帧内无气泡、GPU 利用率 ≈99%**
- **CUDA Graphs 实测否决**：`trtexec --useCudaGraph` 19.771 vs 19.735 qps = **+0.2%**
  （没有气泡就没有「等 GPU」的时间可供它节省，与 7.0 节的上界证明互相印证）

### 11.6 本节仍未闭环的部分

- 用 `--workspace=2048` + 200 帧校准重建的 INT8 引擎**已构建完成并做了 trtexec 三方对照
  （见 11.1b：无增益）**，但**端到端 app A/B 与精度体检尚未跑**（按用户要求先停测试、优先同步文档）。
  工具与步骤：`scripts/verify_new_engine.sh`、`scripts/compare_engines.py`，见 README 第十节
- 用测试视频校准只验证了**性能**；**交付前若真要换引擎，必须用业务真实场景数据重新校准**才能谈精度
- 11.1 里 fp16 慢 17% 的**因果（`--workspace=16`）尚未做对照实验坐实**，
  但结论不受影响：生产用的是 INT8，而 INT8 引擎是健康的
